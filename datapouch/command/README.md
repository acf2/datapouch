# reader-macro.lisp
AKA `:DATAPOUCH.COMMAND.READER-MACRO`

## Intent

Reader macros are a very convenient way to make your own syntax with Common Lisp.
This file streamlines this, despite being somewhat inefficient in implementation.

## Quick how to

To use this file in the intended way, one must set `*RMACRO-CALLBACKS*` and call `INSTALL-COMMAND-READER-MACRO`.
Order is not important, and `*RMACRO-CALLBACKS*` may be changed at any time (which is used later).

Each callback function is given the full string representation of a suspected command.
Then, it must either parse it and do some transformations, returning `(VALUES T <new form to eval>)`, or quickly fail and return `NIL`.
So the intended way to interpret the meaning of rmacro callbacks is to think of them as of combined parser and payload function simultaneously.

E.g.: invocation of
```
/hello senile old man
```
will give reader macro callback the string `"hello senile old man"`

Then, let's suppose that it had been parsed, and the function has returned these values:
```
T
(FORMAT T "Hello, ~:(~A~)!~&" "senile old man")
```
Which will ultimately result in printing
```
Hello, Senile Old Man!
```

Notice that the function had returned a form, despite not being a macro.
This is correct, as that form will be returned from reader macro unchanged and evaluated.

`INSTALL-COMMAND-READER-AUTOPRINT-HOOK` was made for end-user convenience.
E.g.: when commands are shortened down to single characters it is very bothersome to prepend them with the same control character every time.

# `expression.lisp`

Attach functions to named regex groups to parse and handle their values.
Combine them again, and attach another function to process the results.
And again...

## Intent

Idea, that led to writing of that file, was a simple, almost trivial one.
One regular expression has a part that must match some number.
Another one has the same part.
But their respective handlers will need to parse this number on their own.
And handle the possibility that there might be no number at all.
And... so on and so forth.

Regular expressions are a very simple tool.
But why can't there be one singular parser for some reoccuring part, to ease the use of that tool *even further*?
This is the main idea of expressions.

Yes, configuration might look finicky, but it allows extensive control.
Also, expressions now could be considered too low level to be comfortable to use, when there are patterns and pattern-expressions, but everything was built on top of them.
(To the point, that expression-specific parameters like `:USE-ONLY-NAMED-RESULTS` are passed down from pattern-expressions.)

## Summary

Two warnings:
1. This file should not be read before regex-support module. Some parts of expressions depend on it, and might confuse the reader.
2. Expressions now are just another building block of a greater abstraction. They can be used as is, but it is advised to not do this. Refer to patterns and pattern-expressions for more info.

`EXPRESSION` and `LEXICON` classes are two main pillars of this file.
The first one represents some regular expression that is wrapped in a named group, and a handler to process the results of a match.
The second one is the container for such pairs.
One is not used without the other.

Before any controls could be explained, a generic idea of how this works must be understood.
Expression handlers *need* [regex] group tree as their input.
The same group tree that is generated by functions from regex-support module.
Or, if expressions are to be used by themselves, user must provide the input with the same formatting.

There is no such thing as "top handler".
When user generates his terminal handler, he actually inverts control and calls tree traversal with the container of expressions lexically bound.
Traverse function starts walking the tree, and looks for groups.
When it encounters one, it looks group's name up in expression container, and if a match is found, traverse function applies the corresponding handler from the pair.
Leaves are handled before their parent is, which means that the parent group's handler can work with much more abstract parameters.
E.g.: if some subexpression means "some data from the database [with these constraints]", then parent group's handler could receive a table slice as its argument, that had been fetched by child's handler function.
And, as expected, terminal handler is called last and called always.
This means that it does not need to be stored in lexicon (and really shouldn't).

Besides the call order, terminal regex won't have any user info attached to it to be passed as a first argument to a handler.
Why? Because it has no associated named regex group, and, as a consequence, no place to store such contextual info.
This can be circumvented relatively easy, so it is not considered a bug.

Then, the short explanation of usage boils down to:
- stuffing a lexicon (= container) with expressions, which might be encountered during parsing;
- using regexes from this lexicon to compose other regexes;
- creating a terminal handler (user handler) to process the result of a match.

As an important note, regexes from a lexicon could be used in composition of other regexes for the same lexicon.

## Quick how to

Barring the above explanation, actual usage is relatively easy.

- An object of `LEXICON` class should be created.
- Then, it must be populated with expressions, using any appropriate method.
The most simple one is using `SET-IN-LEXICON` / `GET-FROM-LEXICON` pair of functions, as it allows to forget that `EXPRESSION` class even exists.
- After all of it, and creation of a termanal regex (which should not be added to the lexicon), user handler must be wrapped with lexicon, using `WRAP-WITH-LEXICON` function.
This will result in a lambda, that will demand only one argument: group tree, that had been produced from a match of the terminal regex.
And this lambda will transform or process the group tree, according to user handler.

### Named results

*Very important note* should be made here.
Even tree-like products of a regex match are hard to read.
`expressions.lisp` has an *enforced by default* setting to make user handlers more readable.

Parameter `:USE-ONLY-NAMED-RESULTS`, which corresponds to a slot of `EXPRESSION-CONFIG` class, controls this.
When set to `NIL`, no additional work is necessary, but user handler will receive regex match "as is" without any processing whatsoever.
When set to `T` (which is the default), everything from the group subtree will be stripped, besides objects of `NAMED-RESULT` class.
They, instead, will be converted into a keyword arguments for the handler.

**Example**:
Let's suppose that current regex had a match, that was parsed to a group tree.
```
(:example-group <USER-INFO> "12" (:number <USER-INFO> "3") "4")
```

`:number` is a valid expression-type for current lexicon, and its handler returns an object of `NAMED-RESULT` class.
Again, let's suppose that this handler returns the result of a call to `(MAKE-RESULT :pies-in-the-sky 3)`, because `:pies-in-the-sky` had been in its user info, or something like that.

Then, just before the handler for `:example-group` is called, the group tree would look like this:
```
(:group-name <USER-INFO> "12" <NAMED-RESULT :pies-in-the-sky 3> "4")
```

There are two distinct possibilities here:
- If `:group-name` expression had been defined with `:USE-ONLY-NAMED-RESULTS` set to `NIL`, then the handler will be called like this:
```
(FUNCALL user-handler <USER-INFO> "12" <NAMED-RESULT :pies-in-the-sky 3> "4")
```
- On the other hand, if `:group-name` has a setting `:USE-ONLY-NAMED-RESULTS` set to `T`, the call will be:
```
(FUNCALL user-handler <USER-INFO> :pies-in-the-sky 3)
```

Obviously, some handlers *must have* `:USE-ONLY-NAMED-RESULTS` set to `NIL`, or nothing will ever be done: `NAMED-RESULT` instances aren't generated by regex-support module.
But usually, it's the simplest ones, like parser of integers in the example above.
Impact to readability of user handlers' lambda-lists is considerable though.
Function `MAKE-RESULT` hides the fact that some class is involved altogether.

# `pattern.lisp`

A specific command generation tool, that is expected to work alongside readline functionality, as well as to fulfill creator's specific gimmicky requirements.

## Intent

What kind of requirements were there for command system of Datapouch?

Commands should work, yes. And then? Maybe short versions of commands, to spare the user effort of typing them each time in full? Oh, maybe autocompletion? But... short versions look promising too. Maybe, make some form of "learn-as-you-go" autocomplete, that will expand any correct short-form command into a full form? To show user what was just entered before command is executed? And what about documentation?...

Scope's too big, time's too short, resources are too few. But! There is a catch.

In the same vein as sampled regexes, all these could be divided to the most basic elements, written as elementary "blocks" and then combined, concatenated, etc.
Cognitive load to fully define one tiny "block" is negligible. But combination allows these blocks subsequently define how big, complex commands will behave.

Five avenues were considered:
- command execution;
- short command execution;
- short command expansion;
- classic autocomplete;
- docform, to be used in documentation.

Some of them, in certain circumstances, have the same meaning. E.g.: most immutable command words like "go", "save", "quit" and so on, are fit to be used in autocomplete lists *and* in help for the command. Same goes with short command execution/expansion. The parser (in particular: regex) is the same, the only difference is how it will be used.

This proved to be a fine mess: decoupling them seemed like a very bad idea. But handling all five as one type of object? Counterintuitively, this was easier.

## Summary

When you have a hammer, every problem starts to look like a stuck out nail.
In the same manner, incapsulation of `pattern.lisp` was done similar to `expression.lisp` file.
There were regexes and handler functions, that constituted a pair - expression.
Here are patterns and many handler functions, that constitute another object - behavior.

Explanation of usage is insultingly familiar:
- stuff a behavior-container with behaviors, which might be involved;
- use patterns from this behavior-container to compose other patterns (and maybe use them for other behaviors);
- create functionality to take advantage of this (either terminal [user] handler, expansion handler, autocompletition list or docforms).

Yet, while solving the problem aforementioned in the 'Intent' section, `pattern.lisp` is clumsy to use.`pattern-expression.lisp` is complimentary code, that takes care of trivial cases (like constant words), combinations of patterns (making the usage more organic and less forced), and behavior-container utilization (connecting `pattern.lisp` machinery to framework user). Basic non-trivial patterns (like wildcards) are still required to be handled with functions from `pattern.lisp`, but just about anything else had been made easier.

## Quick how to

No. Nope. Nah-nah-nah, I'm not doing that. Go to 'how to' of `pattern-expressions.lisp`.

# `reader-macro.lisp` symbols

## External

### `*ENABLE-EXECUTION*`
Controls whether successfully read reader macros will be evaluated, or simply discarded.
Default: `T`

### `*RMACRO-CALLBACKS*`
List of functions, each of which represents a tandem of parser+processor to be called.

Each function must take one argument:
1) String value, representing a possible command to be parsed and evaluated.

Each must return two values:
1) `T` or `NIL`, that will indicate, was parsing successful or not,
2) Resulting form to be evaluated/returned from macro, if command had been parsed successfully (= the first return value had been `T`).

### `*STOP-CHARACTERS*`
`COMMAND-READER-MACRO` will read all characters from the stream up to any character from this list.
If you want commands to contain any of these chars, or want `COMMAND-READER-MACRO` stop at others, then change the variable.

Default: `(LIST #\newline #\;)`

### `*CONTROL-CHARACTER*`
It is merely a suggestion for control character, which is to be used with `SET-MACRO-CHARACTER` during set up phase.
It was made into a dynamically bound variable to alter previously written code with more ease, if need arises.
Otherwise, `INSTALL-COMMAND-READER-MACRO` has perfectly reasonable `:CHARACTER` keyword argument.

Default: `#\/`

### `INSTALL-COMMAND-READER-MACRO`
Lambda-list: `(&KEY ((:CHARACTER CHARACTER) *CONTROL-CHARACTER*) ((:READTABLE TABLE)))`

Before anything could be done, reader must recognize the need to call new macros.
This is the chosen method of this module.
Adds character to designated readtable, allowing the reader to call `COMMAND-READER-MACRO` function (and iterate over rmacro callbacks).

NB: `NON-TERMINATINGP` is set to `T` because the default `#\/` character is too common.
* [CLHS: SET-MACRO-CHARACTER](https://www.lispworks.com/documentation/HyperSpec/Body/f_set_ma.htm);
* [SO: "What does the non-terminating-p argument of set-macro-character do?"](https://stackoverflow.com/questions/30699851/what-does-the-non-terminating-p-argument-of-set-macro-character-do).

### `INSTALL-COMMAND-READER-AUTOPRINT-HOOK`
Lambda-list: `(&KEY ((:CHARACTER CHARACTER) #\/))`

`cl-readline` library has several hooks that could be configured.
Since usage of these reader macros relies heavily on one character, it could be beneficial to add this character as a prefix to any user input.
This function does exactly that: it adds a pre-input hook that inserts control character as a first character.

## Internal

### `READ-LINE-UP-TO`
Lambda-list: `(STREAM STOP-CHARACTERS)`

Reads line character by character, with `PEEK-CHAR`+`READ-CHAR` up to one of characters from `STOP-CHARACTERS` list.
* [SO: "Appending character to string in Common Lisp"](https://stackoverflow.com/questions/18045842/appending-character-to-string-in-common-lisp);
* [SO: "Read input into string in Lisp reader macro"](https://stackoverflow.com/questions/30942815/read-input-into-string-in-lisp-reader-macro).
NB: Probably, one will need to allow recursive calls for peek/read-char in case if this file is combined with more "tame" and "sane" reader macro usage, i.e. not string/regex based.

### `RETURN-TO-STREAM`
Lambda-list: `(STRING STREAM)`

Unreads the whole string character by character.

### `COMMAND-READER-MACRO`
Lambda-list: `(STREAM CHAR)`

Common wrapper function for all reader macro callbacks.
If callback call isn't successful, returns all characters back, beside reader macro character.
